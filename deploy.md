## 1. External LLM answer model — GDPR / data-processing (added: Sprint 2b)

The employee chat (Sprint 2b) sends the **employee's question + retrieved convenio text** to an external LLM provider (default **Claude API**) to synthesise the answer. That means personal data of Sedena staff is processed by a third party on every answer, which triggers EU/Spanish GDPR obligations. **All three must be satisfied before go-live:**

- [ ] **EU / approved endpoint.** Use the provider's EU-region (or otherwise approved-for-EU) API endpoint, so data isn't processed in a region without an adequate-protection basis. *(Sprint 2b-1 wired this as non-secret config: `HR_AI_ANSWER_MODEL` / `HR_AI_ANSWER_ENDPOINT` on `hr-backend` — passed to `hr-ai /synthesise` per call. These **must** point at an EU-available model/endpoint before go-live.)*
- [ ] **EU / approved endpoint for the ROUTER and GROUNDING calls (added: Sprint 2b-2).** 2b-2 added two more provider calls that see the employee's **question** (`/route`, ADR-0016) and the **question + answer + cited convenio text** (`/ground`, the per-claim grounding check). `/ground` uses the answer model (same `HR_AI_ANSWER_ENDPOINT`, already covered above). `/route` uses a **separate router model** (`HR_AI_ROUTER_MODEL`) and a **`HR_AI_ROUTER_ENDPOINT`** that **defaults to the answer endpoint** — *but if it is set to a distinct endpoint, that endpoint must independently satisfy all three obligations here (EU region, signed DPA, zero-retention).* Verify the router endpoint is EU before go-live, or leave it defaulted to the (already-vetted) answer endpoint.
- [ ] **Signed Data Processing Agreement (DPA).** A signed DPA must be in place with the answer-model provider — the contract (legally required when a third party processes personal data on your behalf) committing them to: use the data only to provide the service (**no training on it**), keep it secure, not retain it, and act only on Sedena's instructions as controller. Anthropic offers a standard DPA — sign it. *(Covers the answer, router, and grounding calls when they share a provider/endpoint; a distinct router endpoint needs its own DPA.)*
- [ ] **Zero data retention enabled.** Turn on the provider's zero-retention / no-logging option so the question + convenio text are not stored by the provider after the answer is returned. (DPA + zero-retention go together; applies to the router + grounding calls too.)

**Why:** Spain's data-protection authority (**AEPD**) and Sedena's **comité de empresa (works council)** will expect a signed DPA and a clear data-flow story; a missing DPA is a common go-live blocker (see `roadmap.md` Sprint 9 — privacy/GDPR hardening, and the works-council sign-off that can gate deployment).

**Note added Sprint 10-M (2026-09-12), same posture, one new visible knob.** `claude-sonnet-5` (the Claude 4.6-generation and later models) exposes a per-request `inference_geo` parameter (`"us"` or `"global"`; no `"eu"` value exists on the first-party API). Left unset, it defaults to `"global"`. This is **not a change in data-residency posture** — the pre-Sonnet-5 answer model never had this parameter at all and was already processed under the same no-EU-guarantee terms (Anthropic's own docs: workspace storage is US-only regardless; the DPA + EU SCCs above are what actually cover the transfer, not a region toggle) — but it is now an explicit, visible setting where before there was none, so it's worth this line before someone assumes "global" means "not vetted." If a true EU-region requirement ever supersedes the DPA/SCC posture, the fix is on Anthropic's side (an EU inference region, waitlisted as of this writing) or a hyperscaler route (Bedrock/Vertex in an EU region) — not something `inference_geo` alone can deliver today.

**Note (not a deploy item — design fact, built in Sprint 2b-1, extended 2b-2):** the API key is **never** in the browser and **never** in plaintext — it's set once in the admin "Answer model" screen, encrypted at rest (`Crypt`, app-key, in `answer_model_settings`), shown masked (`••••1234`, reconstructed from `key_last_four` without decrypting), and rotatable but not readable back. The frontend never calls the provider directly; only `hr-backend` does, decrypting the key in `ChatService` for the turn and passing it in the request **body** (never a header) to `/route`, `/synthesise`, and `/ground` (the same key path for all three — ADR-0015/0016), never persisted by `hr-ai`.

- [ ] **HR task — assign employees to their group (added: Sprint 7f, ADR-0028).** A group-scoped fact only answers for an employee whose `employees.convenio_group_id` is set, and **no path ever sets it without a human** (ADR-0028 §7). Two surfaces, both requiring a person:
  - **The directory picker** — `convenio_group_id` on the employee form, listing that convenio's **approved** nodes parent-first (`Grupo 2 › resto áreas`). It pre-fills from the job category's approved memberships **as a suggestion only**, and only when the field is empty; changing the job category clears it rather than silently re-deriving. The API refuses a node from another convenio (422) and refuses a node that is not `approved` (422).
  - **The CSV `group` column** — *one* optional column, not two. A sub-area is addressed as `Grupo 2 > resto áreas`, with the `>` explicit so no delimiter is ever guessed; either side may be the printed label (`Grupo 2`, `resto áreas`) or the normalized code (`2`, `resto-areas`), since `GroupCodeNormalizer` collapses both onto one key. **A single column is deliberate:** a sub-area has no meaning without its parent, so two columns would make a half-specified scope (`sub_area` filled, `group` blank) expressible, and the importer would then have to interpret it. **An ambiguous row fails** with both candidates named — `todas las áreas` can legitimately exist under Grupo 1 *and* Grupo 3 — and a convenio with no approved tree yet fails with a message saying so, rather than writing a null. Same discipline as the matcher: never guess a scope.

  Until a group is assigned, those employees **escalate** rather than get a wrong answer. That is the safe default and still a coverage gap someone must close on purpose. Currently **1 of 14** staging employees has a node.
- [ ] **Approve a convenio's group tree before relying on it (added: Sprint 7f).** Proposed nodes arrive `ai_agent`/`needs_review` and are **invisible to the matcher** by design, so a convenio with an unapproved tree answers exactly as it did before 7f (Tier 2 inert, not broken). Six convenios were proposed and scored 31/31 exact on staging; **only convenio 21 is approved** (5 nodes, 8 fact bindings). **Five remain pending — 3 (COEAS Álava), 4 (COEAS Andalucía), 11 (COEAS Estatal), 18 (Acción e Intervención Social Navarra), 19 (COEAS Navarra) — 28 `needs_review` nodes and 66 proposed category memberships.** Two verified group-labelled facts (41 on convenio 3, 79 on convenio 4) are blocked on nothing but that reviewer pass. Approving a node also requires confirming its **fact-binding diff**: approval alone binds nothing.

## 4b. The semantic conflict fence — pre-go-live obligations (added: Sprint 7d)

Surfaced measuring `fence:calibrate-semantic` and `succession:gold-eval` against the real staging corpus (see `sprints/sprint-07d/review.md` §2 for the full numbers). The fence code (ADR-0024) is built, tested (112/112 backend tests), and its thresholds (`semantic_conflict_threshold = 0.78`, `semantic_review_band = 0.66`) are calibrated from real anchor scores — but neither of these findings is a code defect; both are **corpus state** that must be addressed before the fence does its intended job in production:

- [ ] **Topic-tag the active convenios before go-live.** No document in the corpus carries a topic tag today. The Sprint-5 structural fence term treats an untagged in-scope convenio as governing (fail-closed: `orWhereDoesntHave('topics')`), so **every** ruling publish attempt is blocked by the structural term alone, before the semantic term is ever consulted — confirmed live on staging (a near-verbatim overlap attempt against an untagged scope returned `409 topic_scope_conflict` with `passages: []`, i.e. hr-ai wasn't even called). Until tagging exists, the escalation-resolution flywheel (Sprint 4) cannot publish a single ruling, calibrated fence or not. *Pre-go-live action:* run the Sprint 7a tagging-proposal pipeline over the active convenio set and have a human verify each proposed tag, so real rulings have a topic to be compared against.
- [x] **COEAS Estatal (`numero` 99100055012011) — corrected (Sprint 7e): NOT a text-layer gap; a tagging-only item.** This item previously tracked it as a scanned/no-text-layer convenio needing OCR (re-discovered by the fence calibration: anchor a5, convenio active, `eligible: 0`). Querying staging's `document_pages` directly for the Sprint 7e eval (plan.md §1.7) found the opposite: COEAS Estatal has a **full text layer** (74/74 and 62/62 pages with extractable text across its two documents) — `eligible: 0` there is a **retrieval/embedding-state gap** (likely simply not yet chunked/embedded, or a scope resolution gap), not an OCR problem. **It is dropped from the Sprint 7e OCR backlog** (it was never a real member of it) and left as a pure tagging/embedding-verification item — *pre-go-live action:* confirm it is chunked and embedded with the correct scope, independent of any OCR work.
- [ ] **The fence thresholds are calibrated on n = 2 anchors per class.** Only 2 of the 5 convenios the anchor fixture (`sprints/sprint-07d/eval/anchors.json`) references have an active `official_convenio` text to compare against; the class-(a)/(b)/(c) statistics in `review.md` §2 rest on those 2 scores per class alone, and the two classes already **overlap in score space** at this sample size (the strongest same-topic-other-point anchor, 0.8751, scores higher than either near-verbatim paraphrase anchor). That is a small-N artifact, not proof the classes are inseparable, but it means the current threshold (0.78) over-blocks any real gap-filling ruling that scores like the strong same-topic anchor did. *Pre-go-live action:* as more convenios gain active official text (tracked in §5) and the corpus gets topic-tagged (above), widen the anchor fixture and **re-run `fence:calibrate-semantic --json`**, recording the new numbers in `sprints/sprint-07d/review.md`. Do not treat 0.78/0.66 as final until n grows.

### Salary-PDF conversion runbook — `salary:pdf-to-xlsx` (added: Sprint 7e follow-up, docs 12/27/57)

The route from a salary grid printed in a PDF to `salary_tables` rows an employee can be told (flow 2b in `corpus-coverage.md`). `salary:import` and hr-ai's `salary.py` are **never** modified for this; every accommodation happens in the derived `.xlsx` before the importer sees it, and every step is human-gated:

```
salary:pdf-to-xlsx --document=<pdf-uuid>          # OCR table pages + write derived .xlsx + PROPOSE a header mapping
  → human compares each sheet to the page image (the review table prints a 10-min signed link per page)
salary:pdf-to-xlsx --document=<pdf-uuid> --apply-header-mapping   # only on approval; rewrites row 1 ONLY
salary:pdf-to-xlsx --document=<pdf-uuid> --verify                 # read-only parse: is the grid detected now?
salary:import --document=<derived-uuid>                            # the unmodified importer
salary:pdf-to-xlsx --document=<pdf-uuid> --mark-provenance          # source=ocr_pdf + restore verbatim headers
```

Gazette conventions found in the real corpus, and what each requires. Expect these; do not let the command "handle" one silently:

1. **Stacked bilingual grids (Basque above Spanish, one page, one grid).** Docs 12/27 (Gipuzkoa) print the same table twice on one page — the `eu` header/rows, then the `es` header/rows — and the OCR faithfully returns it as ONE `table_rows` array with a second header row buried in the middle. Left alone, the importer reads the Basque rows as data rows and mints duplicate job categories in the other language. The command detects the second `Categoría`-headed block and keeps **only the Spanish table**, recording every dropped row verbatim on the `Notes` sheet (approved decision, `sprint-07e/review.md` §5). *Check on review:* the sheet's row count should equal the number of categories on the page, not twice it, and the Notes sheet should say which rows went.
2. **Units inside the header cells (`(mes)`, `(año)`, `(€)`, `(€/hora)`, `(sin antigüedad)`).** `salary.py` matches header cells against its synonym vocabulary **exactly**, so `"Salario base (mes)\n(€)"` matches nothing and the whole sheet is skipped with `no salary-grid header found` — a **silent zero-row import**, which is the failure mode to watch for. The fix is deliberately NOT normalization inside the importer (`(mes)` vs `(año)` is semantically load-bearing — it decides whether a figure is monthly or annual): the command *proposes* a mapping per column, prints the canonical vocabulary next to the actual cell and the exact qualifiers it would drop, and applies nothing until a human approves. A qualifier that would *contradict* the target field (a `(mes)` header proposed onto an annual field) is flagged unsafe and never proposed. **The approved condition:** `--mark-provenance` restores each mapped column's original header text, verbatim, as an extra `raw_values` key on every imported row (`"Valor hora (sin antigüedad)\n(€/hora)" => "20,35"` alongside the importer's own `"hora"`), and the dropped qualifiers are listed on the Notes sheet — so a stripped caveat is never lost, only relocated. Note that re-running `salary:import` rewrites `raw_values` from the sheet: **re-run `--mark-provenance` after any re-import.**
3. **Year-column grids (`CATEGORÍA | 2025 | 2026`) — convert with `--year-columns`, never with a header mapping.** Doc 57 (Ocio Educativo Álava) prints one column per *year*, with the unit inside every cell (`36.343,74 euros`), which `salary.py`'s model — one column per pay concept — cannot represent as-is. Two specific traps: `_looks_like_hours_header()` matches any bare 3–4 digit header, so `2025`/`2026` would be read as the *hourly-rate* column; and `_is_number("36.343,74 euros")` is false, so every data row would be discarded. Before Correction-salary-01 that combination produced a **0-row no-op that reported success**; `salary:import` now fails loudly on it instead. The approved transform is `salary:pdf-to-xlsx --document=<uuid> --year-columns`: one sheet **per year** (pages merged, since the grid continues across pages under a repeated header and two sheets of the same year would collide on `(convenio_id, year)`), the header rewritten to `<label> | Salario anual`, and the literal `" euros"` suffix removed from the values. Both alterations are recorded on the Notes sheet and the untouched grid stays in the OCR sidecar. No monthly is synthesized — the source states none, so `base_salary_monthly` is NULL and the chat answers the annual only (ADR-0027). *Also note:* the caption around such a grid may never state whether the figures are annual or monthly — doc 57's page says only "Subida salarial año 2026" and, in the acta prose, a 3,9 % uprate; the two year columns are verifiably the same quantity (36.343,74 × 1,039 = 37.761,14), but *which* quantity is a human reading, not an inference the tool may make. That reading is what licenses the `Salario anual` header, and it belongs in the sprint review, not in the tool.
4. **The sheet name carries the year, and the year decides identity.** `salary:import` keys `salary_tables` on `(convenio_id, year)` and **deletes and replaces** that table's rows; `salary.py` reads the year from the **sheet name** (`_year_from_sheet_name`). A year-less name (`"Page 2"`) therefore imports as `year = NULL`, and every year-less table of one convenio collapses onto a single row — importing a convenio's 2026 table would have silently deleted its 2025 rows. Derived sheets are consequently named `"<year> (page N)"`, with the year taken from the page's own OCR'd title (then the document title/filename/`validity_start`, never inferred from the figures) and its provenance recorded on the Notes sheet. *Check on review:* the `year` column of the review table must be right for every sheet, and two sheets resolving to the same year raise an explicit warning — heed it, it means one grid is about to overwrite the other.

**When NOT to convert a salary PDF** (both are live examples, deliberately skipped): the PDF is superseded by a newer table for the same convenio while still flagged `retrieval_status = active` (doc 59); the convenio's prose has expired with no successor loaded, so the figures would have no current convenio text behind them (doc 94 / convenio 5). Converting either produces answers that are wrong in a way employees can't detect.

**The accuracy caveat this runbook used to carry is now fixed, and the fix changes what to check.** `salary.py` no longer derives `base_salary_monthly = gross_annual / 14` (Correction-salary-01 / ADR-0027) — the monthly comes from the source's own monthly column or is NULL, and `pagas_count` is stored only when a header states it. Two consequences for this runbook: a mapping proposal that lands a `(mes)`-qualified header on `base_salary_monthly` is now **consistent** rather than lossy (the proposal says so), and after **any** re-import you must re-run `--mark-provenance` (the importer rewrites `raw_values` from the sheet) and then `salary:audit-monthly`, which exits non-zero if any stored figure has no source cell behind it.

**Third consequence (follow-up):** `--mark-provenance` also restores the original OCR'd header into `salary_table_rows.base_salary_monthly_label`, not just into `raw_values`. The chat names each monthly figure by its source column (`salario base mensual…`, `bruto mensual…`, `importe mensual en 14 pagas…`), so after a re-import the label is the *mapped* header until this step runs — the figure is right either way, but the name the employee is told should be the gazette's.

## 6a. The eyes-on rule — employee chat in a real browser, every sprint (added: Sprint 8, 2026-09-11)

- [ ] **Every sprint's close must include exercising the employee chat in a real browser, against the actual deployed host — not just via `curl`/API tests, `otp.sh`, or artisan tinker.** Found live during Sprint 8's own eyes-on (2026-09-10, `sprints/sprint-08/review.md` §16): `ChatScreen.tsx` called `crypto.randomUUID()` — which the spec requires to run in a **secure context** (HTTPS or `localhost`) — before its own `try`/`catch`, so on staging's plain-HTTP deployment the call threw an uncaught `TypeError` and every chat send silently aborted before any network request fired. This bug has existed since Sprint 2b-1 (the chat UI's original commit) and survived **every** prior sprint's review, because every prior "proof the chat works" this project ever recorded went straight to the API (`curl`, `otp.sh`, direct `POST /chat/message`, tinker queries) and never through an actual browser rendering the actual chat screen against the actual deployed host. **A route-level or API-level test, however thorough, structurally cannot catch a browser-only failure mode** — a secure-context-gated API, a CSS rule that hides a control, an uncaught client-side exception on render/send. *The rule, going forward:* the pre-merge eyes-on pass for **any** sprint — not only ones that touch the chat surface directly — must include logging in as a real seeded test employee, in a real browser, on the actual deployed host, and sending a real message through to a real rendered answer, end to end. A proxy for this (API calls, unit/feature tests, `tsc`/`eslint`/`vite build`) is necessary but never sufficient on its own for this one surface.

## 6b. TLS / a real domain — promoted to a go-live blocker (added: Sprint 8, 2026-09-11)

- [ ] **Staging's `Caddyfile` is plain `:80` — no TLS, no real domain.** This was previously recorded only as an inline comment ("the documented first-bring-up variant, pending a real domain") — a footnote, not a checklist item. It is promoted here to an explicit go-live blocker, because it is not merely a nice-to-have: it **directly caused** the real, user-visible bug named in §6a above. Several browser APIs — `crypto.randomUUID()` among them, but also some clipboard/storage/service-worker APIs a future sprint could reach for without thinking twice — require a secure context and are silently `undefined`/unavailable on plain HTTP; `localhost` dev never surfaces this class of bug (it *is* a secure context), so it is invisible until a real non-localhost HTTP deployment is actually clicked through in a browser. *Before go-live:* a real domain pointed at the staging/production EIP, plus Caddy's automatic HTTPS (Let's Encrypt — no code change needed once a real domain resolves to the host), must be in place — and the employee chat must be re-verified per §6a specifically against the HTTPS host, not staging's current plain-HTTP one, since that is the one difference this bug depended on.

### Sprint 8, Step 1 — `hr-backend-scheduler` (the first scheduler this stack has ever run)

- `infra/compose/leak-scan.sh` — run by `deploy.sh` before every build, not just once (staging plan §4 step 4): scans all four repos, `docker-compose.staging.yml`, and (once present) the built image histories for AKIA-style keys, raw secret assignments, and PEM headers.

- `infra/08-derived-secrets.sh` — added because hr-ai's `config.py` takes ONE composed DSN (`DATABASE_URL`), not decomposed `DB_HOST`/`DB_USER`/... vars like hr-backend does. Composes `postgresql://hr_ai:<password>@<rds-endpoint>:5432/hr_platform` once (RDS endpoint + the already-generated `hr-ai-db-password`, neither typed nor echoed) and stores it whole as `/hr-staging/hr-ai/database-url` (SecureString). - **Item 3 (F-1) — checksum-dedupe no longer silently re-types a document.** A content-hash match on re-ingest previously overwrote `document_type`/convenio/validity unconditionally, using whatever the new call's filename/flags happened to parse to. It now mirrors the manual-edit scope gate exactly: a dedupe hit with a scope-affecting change reports "ya existe como documento N (tipo X)" and changes **nothing**, unless `confirm_scope_change` (HTTP) / `--retype` (CLI) is explicit — which then applies the change and records an `admin_manual` (never `filename_parse`) `TagEvent`. **Operational note:** this changes the behaviour of `documents:ingest-folder` on a re-run over a folder whose files haven't changed bytes but whose surrounding context implies a different type/scope — a case that previously silently "fixed itself" now reports a `retype-blocked` count and requires `--retype` to actually apply.
- **Item 4 (F-2) — binding-aware `facts:scan-duplicates`.** When both facts in a candidate pair have a bound group node (Sprint 7f, ADR-0028), the comparison now uses the **bound nodes** — same node or ancestor/descendant → still a candidate version pair; sibling nodes → **not** a duplicate — falling back to the pre-7g token-overlap heuristic only when at least one fact is unbound. **Staging dry-run proof (before → after, real corpus, re-run and re-verified while writing `sprints/sprint-07g/review.md` §4.3):** 10 pairs → 9 pairs; the three false-positive pairs crossing convenio-21 Hostelería's Grupo-2 sibling split (`45↔44`, `44↔35`, `35↔34` — the split's two sub-area nodes, área 5 and resto áreas) resolve into the two true same-bound-node pairs the old token pass had missed (`45→35`, `44→34`); the true positive `46→36` (same bound node) unaffected; every unbound-fact pair — including the real Navarra Acción e Intervención Social pair (`54→27`) that ADR-0024's original digit-token pass was built to catch — unaffected. The container used for the staging proof was reverted afterward both times (checksum-confirmed identical to its pre-proof state), per the sprint's stop-before-merge gate.
- **Item 5 (F-3) — `otp.sh` no longer extracts a Message-ID fragment as the login code.** Staging's `MAIL_MAILER=log` writes the mail's full raw MIME dump to `storage/logs/laravel.log`; a hex Message-ID frequently contains a run of 6+ consecutive decimal digits that a naive `grep -oE '[0-9]{6}' | head -1` matched **before** reaching the real code lower in the same log entry. The fix anchors on the mailable's own OTP markup line (not headers) and an `awk` state machine keyed on Monolog's one-line-per-record prefix convention selects the **newest** matching record for the specific recipient email + subject, order-independent. Verified end-to-end against real staging (`admin@hr-staging.internal`): request-code → log read → correct 6-digit code extracted (confirmed distinct from that same message's own Message-ID digit run) → verify-code → a real Sanctum bearer token returned.

### Session 8 (Sprint 10a close + Sprint 10-M — a real operational gap found live, and the answer-model upgrade) — complete

**Manual container recreates must export the same env vars `deploy.sh`/`deploy-run.sh` always export, or `docker-compose.staging.yml`'s `${STAGING_EIP}`/`${RDS_ENDPOINT}` substitutions silently resolve to blanks.** Found live during Sprint 10a's close: a `docker compose up -d --force-recreate hr-backend hr-ai` run in a plain SSH session (no `vars.sh` sourced) produced `APP_URL=http://` and an empty `DB_HOST` — **web health kept passing** (`curl /up` → 200; Laravel's `/up` route needs neither a working `APP_URL` nor a DB connection), which is exactly why this is dangerous: it looks healthy. Every `php artisan` invocation, including `--version`, failed immediately with `In Request.php line 385: Invalid URI.` **The rule, going forward: any manual recreate outside a real `deploy.sh` run must first `source hr-docs/infra/vars.sh` and `export AWS_REGION RDS_ENDPOINT STAGING_EIP S3_DOCUMENTS_BUCKET S3_BACKUPS_BUCKET` (the last two aliased from `vars.sh`'s `NAME_S3_DOCUMENTS`/`NAME_S3_BACKUPS`), exactly as `deploy-run.sh` does — and `/up` returning 200 must never be read as proof of artisan-level health; verify with a real artisan command (`migrate:status`, `--version`, a `tinker` call) after any recreate.** Applied correctly for every recreate from Sprint 10a's close onward in this record (this session's own Sprint 10-M work included, both the initial injection and its revert-and-retry).

**Sprint 10-M raised `/synthesise`'s `max_tokens`** from 1024 to 4096 as a narrow, named exception alongside the answer-model swap (§ Models in use, `architecture.md`) — the old ceiling was tuned against `claude-sonnet-4-5`'s shorter completion style and, left in place, silently truncated a fraction of `claude-sonnet-5`'s longer real answers (measured live, not assumed: 2 of 3 samples on one gold question failed to parse before the fix; zero of 54 after — `sprints/sprint-10-M/step3-halt.md` and `review.md` §4.4/§5 have the full record).
