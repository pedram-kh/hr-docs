### 1.3 The embedding path for clustering — confirmed read-only, no new model, no migration

`hr-ai/app/embeddings.py:40-55` already exposes exactly the primitive Sprint 8 needs, decoupled from any DB write:

```40:55:hr-ai/app/embeddings.py
def embed_texts(texts: list[str]) -> list[list[float]]:
    """Embed a batch of texts → list of 1024-dim unit vectors (cosine-ready)."""
    if not texts:
        return []
    _load()
    vectors = _model.encode(
        texts,
        normalize_embeddings=True,  # unit vectors → cosine == dot product
        batch_size=16,
        show_progress_bar=False,
    )
    return [[float(x) for x in row] for row in vectors]


def embed_query(text: str) -> list[float]:
    return embed_texts([text])[0]
```

But **no existing endpoint returns raw vectors**: `/retrieve` (`main.py:518-544`) always follows `embed_query` with a scope-filtered `document_chunks` ranking + `count_eligible`; `/compare-scope` (`main.py:567-648`, ADR-0024) always ranks N embedded probes against `document_chunks` via pgvector's `<=>` operator and returns chunks-per-probe, never vectors — and ADR-0024 explicitly considered and **rejected** a bare per-text embed loop as "the zero-hr-ai-change fallback… deliberately not built" (`0024-…md:96`), for a different reason (it can't filter authority in SQL) that doesn't apply here since clustering needs no authority filter at all. There is also **no place to store question vectors in Postgres** — `document_chunks.embedding vector(1024)` is the only `vector` column in the schema (`hr-backend/database/migrations/2026_06_20_131011_create_document_chunks_table.php:44-47`), and ADR-0006 scopes pgvector strictly to corpus prose.

**Decision: add one new hr-ai endpoint, `POST /embed-batch`,** a thin FastAPI wrapper (mirrors `/extract-salary`'s shape: `require_internal_token`-guarded, read-only, no DB access) that takes `{"texts": [...]}` and returns `{"embeddings": [[...], ...]}` by calling `embed_texts()` directly — zero new dependencies, zero DB touch (not even `document_chunks`), consistent with "hr-ai never migrates; no new model" (the model is already loaded for every embed/retrieve/compare-scope call). Cosine similarity for clustering is then computed **in-process in hr-backend** (numpy or pure PHP — see §4.2) over vectors already unit-normalized (`embeddings.py:45`, `normalize_embeddings=True`), so cosine similarity is exactly the dot product — no external library needed for the similarity math itself.

### 1.4 `authority_used` semantics (ADR-0015/0023) — what §1/§7 read

`authority_used` is "computed deterministically from the *cited* chunks so an auditor can see 'answered from the convenio' vs 'answered from the baseline'" (`data-model.md:513`). Three (going on four) values exist in the corpus: `official_convenio`, `national_law`, `internal_hr_ruling` (all pre-7c), plus `structured_reference` (7c, ADR-0023, ranked **below** `official_convenio`/`internal_hr_ruling` and **above** `national_law` in `_AUTHORITY_RANK` — a fact can never outrank a convenio, per ADR-0021's structural bound). `floor_decision.authority_used` is a **list** (a composition turn, ADR-0023 Phase 2, can carry both `official_convenio` and `structured_reference` at once — `data-model.md:511`; the golden-trace regression asserts `['official_convenio']` for a convenio-governed prose turn, `Sprint7cAdditivityRegressionTest.php:146,321`). **This is exactly the signal §1/§7 need**: a turn whose `authority_used` includes `national_law` on a topic where the asker's convenio is registry-active is the coverage smell the spec calls out ("a high 'answered from the Estatuto' share on a topic the convenio should cover").

## 2. Deflection & outcomes (§1)

### 2.1 Definitions — stated exactly

- **A turn** = one `chat_messages` row with `role='user'` and its paired `role='assistant'` reply (if any), joined via `message_traces.message_id → chat_messages.id` on the **assistant** message. An `hr_agent` row (`chat_messages.role='hr_agent'`) is **never** a turn in this sense — it "carries no `message_traces`/`message_citations` row" by construction (`data-model.md:479`), so it is structurally excluded from every `message_traces`-keyed query, not filtered out by a `WHERE`.
- **Answered** = a turn whose `floor_decision.outcome = 'answer'` (present regardless of path — salary, reference_fact, reference_fact_composition, or prose).
- **Escalated** = a turn whose `floor_decision.outcome = 'escalate'` — this is the population that has a matching `escalation_cards` row via `chat_messages.id = escalation_cards.source_message_id` (the **user** message, per the base migration `2026_06_20_131021_…:15`, **not** the assistant message — the deflection join must use the source *user* message id, not the trace's message id, when joining to cards).
- **`needs_category`** = a distinct third outcome (`floor_decision.outcome = 'needs_category'`), salary-path only (`data-model.md:513`'s `salary.outcome` enum, mirrored into `floor_decision.outcome`) — the single-turn constrained category pick (ADR-0016's "parked multi-turn clarifier" boundary). **It is neither answered nor escalated**: no card is created, no answer is shown, the turn is a mid-dialogue prompt. **Decision: `needs_category` turns are excluded from the deflection-rate denominator** (they are not a completed exchange yet) but are counted and shown as their own tile ("N preguntas de salario pendientes de categoría") — hiding them would understate salary-path friction, and folding them into "answered" or "escalated" would misstate both.
- **Deflection rate** = `answered / (answered + escalated)`, exactly as the spec states it (`sprint-08-spec.md:16`), computed **per period + scope filter**, with `needs_category` reported alongside but not in the ratio.
- **`hr_agent` turns counted separately** (spec's explicit instruction): an `hr_agent` chat_messages row is **human work performed inside an escalated conversation**, not a bot answer. It is counted as its own tile ("respuestas humanas en chat: N") keyed by `author_admin_id`, joined for a per-agent breakdown — this reuses exactly the same `author_admin_id`/`Admin` relation Sprint 4 already wrote (`ChatMessage.php:21-25`). It never enters the answered/escalated ratio (an `hr_agent` message has no `message_traces` row to have an `outcome` in the first place — this is enforced by the schema, not a query choice).
- **Path split**: `floor_decision.path` when present (`salary_sql`, `reference_fact`, `reference_fact_composition`, `salary_prose_crosspath`); **`prose`** is the implicit fifth value when `path` is absent but `retrieval`/`synthesis` blocks are present (i.e. the turn went through Check A/B/C, per `data-model.md:511`'s `floor_decision` shape). The query must synthesize this fifth bucket explicitly — see 2.2's SQL — because `path` is `NULL`, not `'prose'`, on every legacy prose turn (a deliberate finding from §1.1, not an oversight to "fix").
- **`authority_used` split**: convenio-governed (`authority_used` array contains `official_convenio` or `internal_hr_ruling`) vs Estatuto-baseline-only (`authority_used = ['national_law']` exactly, no convenio member) vs `structured_reference`-involving. The spec's coverage-smell framing (§1) is realised as: *for a topic where the asker's convenio is registry-active, what fraction of answered turns cite only `national_law`?* — this needs the coverage join from §5, not a standalone query; §2 reports the raw split, §5's screen is where the smell becomes actionable (cross-referenced, not duplicated).

### 2.2 The exact SQL shape (the `stats:deflection` command's core query)

```sql
-- one row per turn, with the path/authority/outcome columns normalised
-- (this is the query `stats:deflection` runs; the rollup table in §2.4 is
-- populated by running it nightly and storing the aggregate, never the raw rows)
select
  mt.id as trace_id,
  cs.employee_id,
  e.convenio_id, e.territory_id, cv.sector_id,
  am.created_at as turn_at,
  coalesce(mt.trace->'floor_decision'->>'outcome', 'unknown') as outcome,
  coalesce(
    mt.trace->'floor_decision'->>'path',
    case when mt.trace->'floor_decision' ? 'retrieval_score_floor' then 'prose' end
  ) as path,
  mt.trace->'floor_decision'->'authority_used' as authority_used
from message_traces mt
join chat_messages am on am.id = mt.message_id and am.role = 'assistant'
join chat_sessions cs on cs.id = am.session_id
join employees e on e.id = cs.employee_id
join convenios cv on cv.id = e.convenio_id
where am.created_at between :period_start and :period_end
  -- scope filter (optional): and e.territory_id = :territory_id / cv.sector_id = :sector_id / e.convenio_id = :convenio_id
```

`hr_agent` turns are a **separate** query (no `message_traces` join possible or needed):

```sql
select author_admin_id, count(*) as reply_count
from chat_messages
where role = 'hr_agent' and created_at between :period_start and :period_end
group by author_admin_id;
```

### 2.3 Period/scope filters

Period: day/week/month, per spec — a `date_trunc('day'|'week'|'month', am.created_at)` group. Scope: territory (`e.territory_id`), sector (**joined through `convenios.sector_id`**, per §1.1's finding that `employees` has no direct `sector_id`), convenio (`e.convenio_id`). All three are simple equality filters on the query above — no new denormalized columns needed on `message_traces` (the join path already exists via `chat_sessions.employee_id`).

### 2.4 Rollup strategy — decided for 1,500-employee scale

**Decision: a nightly aggregate table, `analytics_daily_rollups`, not live queries on every dashboard load — but seeded/refreshable on-demand too, because staging traffic is currently near-zero and a screen that only ever shows "no data yet" until a cron fires is a bad eyes-on.**

Reasoning: at 1,500 employees with the observed thin-but-real turn rate, a full-corpus scan of `message_traces` (jsonb `->` extraction, no functional index) on every page load of *Analítica* is exactly the "row scan on every load" the spec's risk section forbids (`sprint-08-spec.md:63`). But a purely nightly cadence is wrong for a **pre-go-live** environment where the whole point of the screen is same-day feedback during the eyes-on session and the early data-pass. **Resolution: the rollup table is populated by `stats:rollup --date=YYYY-MM-DD` (defaults to yesterday, idempotent per date — delete-then-insert, not upsert-per-row, so a re-run is a clean replace), and the *screen* additionally supports an explicit "refresh today" action** that runs the same command for `today` synchronously (cheap: one day's `message_traces` rows, not the whole table) — this covers both cadences with one code path, no separate "live" query logic to maintain and keep consistent with the rollup's definitions.

`analytics_daily_rollups` columns (additive migration, §11): `date`, `territory_id` (nullable — a `null` row is the "all territories" total, avoiding a separate totals table), `sector_id` (nullable), `convenio_id` (nullable), `path`, `authority_used_key` (a sorted-and-joined string of the `authority_used` array — e.g. `official_convenio` vs `official_convenio+structured_reference` vs `national_law` — so the coverage-smell split from §2.1 is pre-computed, not re-derived per view), `outcome`, `turn_count`. One row per (date, territory, sector, convenio, path, authority_used_key, outcome) combination that actually occurred — sparse by construction, which is exactly right for a thin corpus (no row for a combination with zero turns). Every dimension besides `date` is nullable so a single rollup run can write both the granular rows and the "all scopes" totals row in one pass (`group by date, territory_id, ... ` with `grouping sets` — Postgres native, no extra logic).

**The `stats:*` command set (each one prints the exact numbers the screen shows, so the "every number reproducible" constraint is a command, not a promise):**
- `stats:deflection --from=DATE --to=DATE [--territory=ID] [--sector=ID] [--convenio=ID]` — prints answered/escalated/needs_category counts, deflection rate, path split, authority split, hr_agent reply count — reading the **rollup table** by default, with `--live` to run the raw query from §2.2 directly (for auditing the rollup against ground truth — this doubles as the rollup's own correctness test).
- `stats:rollup [--date=YYYY-MM-DD] [--from=DATE --to=DATE]` — (re)computes `analytics_daily_rollups` for one date or a range; this is the nightly job **and** the manual refresh, same code, per the decision above.

### 2.5 Cron reality (flagged, not solved this turn)

Per TL;DR point 7: there is no scheduler wired up in this codebase today (`routes/console.php` is a stub; no `withSchedule()` in `bootstrap/app.php`; the only always-on background process staging runs is the `queue:work` worker, ADR-0025). **Build-order decision (§11): Sprint 8 adds the Laravel scheduler (`bootstrap/app.php`'s `withSchedule()`, calling `stats:rollup` daily) as a small, additive infra change, plus one cron line added to `hr-docs/infra/compose/docker-compose.staging.yml` (a `schedule:work` process, mirroring the existing worker service's pattern exactly — same image, different `command:`) — not a new service, not a new container image.** Until that lands, the "refresh today" manual action from §2.4 covers the eyes-on session.

## 4. Top/unanswered questions (§3)

### 4.1 Topic-anchor grouping — reuse `TopicLexicon` as-is

`TopicLexicon::matchTopicKeys(text)` (`hr-backend/app/Support/TopicLexicon.php:80-93`) already maps free text to one or more of 14 topic keys (`vacaciones`, `jornada`, `permisos`, `periodo_prueba`, `trabajo_distancia`, …) via accent-insensitive substring anchors — this is the **exact** "existing topic lexicon" the spec names (`sprint-08-spec.md:20`), already used both for the precedence re-rank and the 7c reference-fact pre-check. §3's "top questions by topic" is `TopicLexicon::matchTopicKeys($userMessage->content)` applied to every user turn, grouped and counted — no new vocabulary, no new matching code, a direct call into an existing pure function.

### 4.2 Embedding clustering — algorithm, threshold, medoid, cadence

**Pipeline (nightly, batch — never per-question, never on the employee path):**
1. Pull every **distinct** `user`-role `chat_messages.content` string in the period (dedupe identical strings before embedding — free, since BGE-M3 is deterministic and a repeated exact question wastes a call).
2. Call the new `POST /embed-batch` (§1.3) once per batch (hr-ai's own batching, `embeddings.py:47` `batch_size=16`, already handles the internal chunking) — returns one 1024-dim unit vector per string.
3. **Algorithm: greedy single-link clustering by cosine threshold, not k-means.** Reasoning: k-means requires choosing *k* up front, which is meaningless for a corpus whose true number of distinct questions is unknown and grows over time; a threshold-based approach ("join the nearest existing cluster if cosine ≥ τ, else start a new one") is the standard, simple, deterministic choice for this shape of problem and needs no iteration/convergence step, no random seed, and is trivially incremental (new questions can be assigned to existing clusters without re-clustering everything — relevant once the nightly job has months of history). Since vectors are unit-normalized, cosine similarity **is** the dot product (`embeddings.py:45`) — no separate distance library needed; a plain nested loop with numpy (or PHP `array_sum` of an elementwise product, for a batch small enough that PHP-side math is fine — see the volume note below) computes the full pairwise similarity matrix.
4. **Threshold: τ = 0.80** as the starting point, not a final number (flagged explicitly in §12 as needing calibration against real question pairs once staging has volume) — chosen because it sits just above the `fence:calibrate-semantic` **paraphrase-anchor** band (`semantic_conflict_threshold = 0.78`, `config/hr.php:114`, calibrated on real convenio-vs-ruling text, not questions) as a reasonable prior: two *questions* that are true paraphrases of each other ("¿cuántos días de vacaciones tengo?" vs "vacaciones que me corresponden", the spec's own example) should score at least as high as two paraphrased *passages* did, since questions are shorter and less lexically varied than legal prose. This is an explicit **assumption to validate**, not a measured value — there is no `questions.json` gold set the way `sprint-07d/eval/anchors.json` exists for passages, and building one is out of scope for Sprint 8's read-only-measurement mandate (flagged in §12, not silently deferred).
5. **The label is the medoid** — the cluster member with the highest mean similarity to every other member (never an LLM summary, per the hard constraint) — computed directly from the same similarity matrix, no extra call.
6. **Cadence: nightly**, alongside `stats:rollup` — clustering N≈hundreds of distinct strings is cheap (one embed-batch call + an O(N²) similarity pass, trivial at this corpus's real size) and there is no reason to do it live on a dashboard load. Stored in a new table, `question_clusters` (medoid text, member count, first/last seen, top escalation reason, answer rate) + `question_cluster_members` (cluster_id, message_id) — additive, §11.
7. **"Unanswered" ranking** = `escalation_rate(cluster) × volume(cluster) × sum(headcount of the asking employees' scopes)` — exactly the spec's formula (`sprint-08-spec.md:22`); the headcount term reuses the same `employees` group-by the coverage map needs (§5.2), so this is one shared helper, not two.

**Volume reality check**: per §1.2, staging currently has near-zero real chat volume, so this pipeline will run against a handful of distinct strings for the foreseeable future — which is fine (a threshold-clustering job over 20 strings is instant) but means **the cluster quality itself cannot be meaningfully eyes-on'd until real traffic exists**; the eyes-on criterion for Sprint 8 is that the *mechanism* works correctly (medoid labelling, no LLM, reproducible), not that the clusters are yet interesting.

### 5.1 Building `corpus:coverage` for real — a new service, not a refactor

Per TL;DR #1, there is no command to refactor. **The plan builds `App\Support\CorpusCoverageService`** (a plain PHP class, no framework magic) from day one as the shared query both the admin screen and the `corpus:coverage` artisan export call — so "the screen and the ledger share one query" (the sprint's hard constraint) is true by construction, not by discipline. It generalizes, and sits **beside**, `KnowledgeMap::coverageGaps()` (Sprint 3) rather than replacing it: `KnowledgeMap` stays exactly as-is, still backing the Sprint-3 Map's four gap markers (`unanswerable`, `expired_no_successor`, `suspected_mistag`, `date_expired_active` — a document-level staleness/mistag view); `CorpusCoverageService` is a new, **convenio-level** grid (prose/salary/facts/rulings × every registry convenio) that reuses `KnowledgeMap::PROSE_TYPE_CODES`/`proseTypeIds()` (`KnowledgeMap.php:18-28`, already the exact document-type-code list this needs) rather than duplicating that constant.

Per-convenio, per-type resolution logic (the four ✓/✗ columns, each independently derivable from tables that already exist, confirmed against the ledger's own Part-1 flow descriptions and Part-4 grid):

- **Prose ✓/✗**: `exists(documents where convenio_id=X and document_type_id in PROSE_TYPE_CODES and retrieval_status='active' and exists a document_chunks row)` — reusing `KnowledgeMap`'s "0-chunk = unanswerable" test, but scoped per-convenio rather than listed per-document. Amendment-only flag: `document_type_id = partial_agreement` present but no `convenio_text` present for the same convenio (exactly convenio 9's case in the ledger, "half-covered… coverage is amendment-only").
- **Salary ✓/✗ (current year)**: `exists(salary_tables where convenio_id=X and :year between valid_from and coalesce(valid_to, :year))` — a table for the current year specifically (§12 flags what "current year" means precisely, since the spec's acceptance list calls this out too).

- **Rulings ✓/✗**: `exists(documents where convenio_id=X and authority_level='internal_hr_ruling' and retrieval_status='active')`.

— joined into the grid above by `convenio_id`; ranking is `order by headcount desc` per gap row, exactly per spec ("ranked by people affected"). **Group-level headcount** (for the reference-facts "group-only" case) additionally joins `e.convenio_group_id`, reusing the Sprint-7f column as-is.

`sprint-08-spec.md:26`'s "territory×sector combinations that have employees but no registry convenio at all": `select distinct e.territory_id, cv_missing... ` — concretely, every `(territory_id, sector_id)` pair that appears in `employees ⋈ convenios` (an employee's own convenio's territory/sector, since employees don't carry sector directly per §1.1) has to be checked against whether **any** `convenios` row exists for that exact pair; a pair with employees whose *assigned* convenio exists (by definition, `employees.convenio_id` is `not null` and FK-constrained) can never itself be a "no convenio" row — so this check is actually about the **registry's** full territory×sector matrix (every combination the registry *could* have a convenio for) versus which combinations currently have zero *active* convenios, cross-referenced against whether any employee's *province* matches a gap territory even without a direct convenio link. **This needs the registry's source list** (the same one `registry:import` consumes) rather than a pure `employees`/`convenios` query, since a truly-missing convenio has no row to join from at all. Flagged precisely in §12 as needing one clarifying decision at build time (which registry source of truth enumerates "should exist" pairs) rather than guessed here.

### 5.4 Reason-code vocabulary — reuse the ledger's, now assigned by code

The 8 codes (`SCAN_NO_TEXT`, `UNDER_REVIEW_SCOPE`, `NO_CONVENIO_MATCH`, `SALARY_PDF_NOT_IMPORTED`, `EXPIRED_NO_SUCCESSOR`, `GROUP_SCOPED_FACT`, `FACT_NEEDS_REVIEW`, `MISTAG`) exist today only as hand-written prose in `corpus-coverage-ledger-prompt.md:22-29`/`corpus-coverage.md`. `CorpusCoverageService` assigns them as a PHP `enum` (or class constants — a `match` expression over the same conditions §5.1 already computes), each carrying its own unblocking-action + link (reusing the exact same hash-link builders `EscalationExplainer.php:270-283` already defines — `$documentsLink`, `$factLink`, `$groupsLink` — imported/shared rather than re-invented, since a gap's unblocking surface and an escalation's fix surface point at the same admin screens).

### 5.5 Gaps-closed trend — a snapshot table

`coverage_snapshots` (additive migration, §11): one row per (date, convenio_id, knowledge_type) with the ✓/✗ + reason code at that point in time, written by the same nightly job as §2.4's rollup (or its own `stats:rollup-coverage` command — kept **separate** from `analytics_daily_rollups` because coverage is a state-of-the-world snapshot, not an event-count aggregate, and mixing the two schemas would force nullable columns neither needs). ### 6.2 The stratified draw — deterministic, reproducible from its seed

`quality:sample --month=YYYY-MM --n=N [--seed=INT]` (a new command, precedent-matched to `FenceCalibrateSemantic`'s two-pass structure): 
1. Population = every `message_traces` row for an **answered** turn (`floor_decision.outcome='answer'`) whose assistant message's `created_at` falls in the given month.
2. Strata = `(path, territory_id)` pairs present in that population (per spec: "stratified by path and by territory so a rare path isn't missed") — computed via the §2.2 normalized-path query joined to `employees.territory_id`.
3. **Proportional-with-floor allocation**: each stratum gets `max(1, round(N × stratum_size / total_size))` samples if the stratum is non-empty — the `max(1, …)` clause is exactly what "a rare path isn't missed" requires (pure proportional allocation could round a genuinely rare-but-real path, e.g. `reference_fact_composition` on today's thin corpus, down to zero).
4. **Seeded, reproducible draw**: `--seed` defaults to a value derived from the month string (`crc32('2026-09')`-style, deterministic unless overridden) so re-running the same command for the same month with no `--seed` flag reproduces the identical sample — this is the literal thing `Sprint8QualitySampleStratificationTest` (§11) proves: same month + same seed ⇒ same `message_id` set, and the per-stratum counts match the allocation formula.
5. Each drawn turn becomes one `quality_samples` row, `verdict=null`.

### 6.3 The review screen — one decision per turn

New Review-queue tab, `Calidad` (reusing the exact `ReviewQueuePage` tab pattern, §10): shows the sampled question, the answer with its citations (reusing `EscalationCardDrawer`'s existing citation-rendering, since it already knows how to show a cited answer + trace summary for a card — the same display logic, called on a `quality_samples` row instead of a card), and **exactly three verdict buttons** (correct / partially / wrong) + a failure-kind select (shown only when verdict ≠ correct, per the spec's "kind" field) + a free-text note — "one decision per turn," per the spec's own admonition that HR won't do this monthly if it's tedious.

**Access logging (ADR-0018, non-negotiable per §9):** opening a sample's full conversation calls `ConversationAccessLogger::logView($admin, $session)` — the **same** method `HistoryController.php:110` already calls, with a new `access_type` value is **not** needed (`conversation_view` already fits; only `context` needs a new marker, e.g. `context = 'quality_sample:<uuid>'`, so a `conversation_access_log` audit can distinguish "opened via quality sampling" from "opened via History browse" without a schema change — reusing the existing nullable `context varchar` column exactly as `logSearch()` already does for its own marker, `ConversationAccessLogger.php:41`).

**Reviewer ≠ the agent who handled any related card** (spec's rule): enforced at the point of assignment/display — if the sampled turn has an associated `escalation_cards.assigned_to` (it may not; most sampled turns are *answered*, not escalated, by definition, since the sample population is `outcome='answer'` — so this rule in practice matters only for the rare case a turn was later escalated by a different route, e.g. converted-to-knowledge scenarios are out of scope here) the UI simply excludes that admin from being offered the sample, or the API 422s if that admin attempts to review it. A small, explicit guard, not a structural one — flagged in §12 as a low-volume edge case worth a test but not worth over-engineering given how rarely it can even occur under the population definition above.

### 6.4 "Wrong → task with fix link"

On `verdict='wrong'`: create an `escalation_cards` row exactly like every other escalation-card creation path (reason: a new enum value, `quality_sample_wrong` — additive to the CHECK, §11), with `explanation_facts` populated by a **new** `EscalationExplainer` registry entry (`quality_sample_wrong.<failure_kind>`, five new sub-outcomes mapped 1:1 to the five `failure_kind` values) so the existing `EscalationExplainerGuardTest` machinery extends to cover it rather than needing a parallel explanation path. `fix_link` points back at `#view=review&tab=reference-facts&fact=<uuid>` / `#view=documents` / `#view=directory&emp=<uuid>` depending on `failure_kind`, following the exact same builder-closure pattern already in `EscalationExplainer.php:270-283`.

### 6.5 Monthly trend + roles

`quality_sample_monthly_rollups` — or simply query `quality_samples` directly grouped by `date_trunc('month', created_at)`, `verdict`, `stratum_path`, `stratum_territory_id`: since a month's samples are a small, fixed-size, already-materialized set (unlike the full `message_traces` firehose §2.4 worries about), **no separate rollup table is needed here** — a live `group by` over `quality_samples` is cheap by construction (N samples/month, not N turns/month). Roles: per spec's access matrix (§9), sampling review is `hr_agent`/`super_admin` (mirrors `escalation.work`, reusing that exact ability — sampling *is* escalation-adjacent human work, not a new ability to invent).

1. **`authority_used` distribution on national-law-anchored topics** (§1.4): `select count(*) from message_traces where trace->'floor_decision'->'authority_used' @> '["national_law"]' and trace->'floor_decision'->'authority_used' @> ["national_law"] only` (i.e. Estatuto-only answers, no convenio member) joined to the turn's matched `TopicLexicon` key (§4.1) and the asker's convenio — filtered to cases where that convenio **does** have active prose (per §5.1's prose ✓ check) on the same topic. **A non-empty result here is the exact smell the spec names**: "Estatuto cited where a convenio chunk existed."
2. **The `trabajo_a_distancia` case specifically** — the roadmap and the 2c review both name this exact scenario as the one to watch (`sprint-02c-rechunk/review.md:174,258`: "Silent fallback (gold) | trabajo a distancia — Navarra & Gipuzkoa | answer, `authority=national_law`, cites the Estatuto (doc 73)… the convenio is silent, baseline fills the gap ✓" — **this was the correct, intended behaviour in 2c's own gold set**, not a bug). §8.2's decision rule below distinguishes "correctly falling back because the convenio is silent" (fine, no action) from "wrongly preferring the baseline when the convenio actually speaks" (the re-chunk trigger) — and the 2c gold case is explicitly the *first* kind, recorded here so Sprint 8 doesn't mistake a documented-correct precedent for new evidence of a problem.
3. **The "national-law gold tests"** the kickoff prompt refers to are **not a separate automated test file** — they are the manual gold/round-2 eval table in `sprint-02c-rechunk/review.md` (lines 172-179, 254-258: periodo de prueba 15/30, Gipuzkoa vacaciones 31/26 scope-isolation, trabajo a distancia → national_law) **plus** the automated codification of the *convenio-must-win* half of that guarantee in `Sprint7cAdditivityRegressionTest.php:146,321` (`assertSame(['official_convenio'], $floor['authority_used'])` for a convenio-governed topic). Re-running the 2c gold set's three questions against current staging (unchanged since 2c) plus §8.1.1's real-traffic query **is** "gated on the national-law gold tests" for Sprint 8's purposes — there is no other artifact to point at, and inventing a new formal test suite for this is out of scope for a read-only measurement sprint (the decision is measured and recorded, not re-engineered).

### 8.2 The decision rule

**If** §8.1.1's query returns turns where the convenio has active, on-topic prose **and** the answer used `national_law` only (not "convenio is silent" — that's correct behaviour, see above) — re-chunk. **If it returns zero such turns** (which, given §1.2's near-zero real traffic, is the likely near-term outcome) — record "no evidence, not done" **explicitly**, per the spec's own instruction, rather than silently skipping the item. Either outcome is written to `sprint-08/review.md` with the query and its result, satisfying "the decision is written down with the numbers" even when the numbers are small or zero.

### 8.3 The re-chunk procedure, if triggered

Reuses the 2c splitter verbatim (ADR-0017, already proven on 12 registry-active convenios) applied to doc 73 (Estatuto) specifically — held out of 2c on purpose for exactly this gated-decision reason (`roadmap.md`'s Sprint-2c row: "Estatuto (id 73) held out → Sprint 8 follow-up"). Procedure: re-chunk doc 73 → re-embed (idempotent, per 2c's proven re-embed path) → re-run the three 2c gold questions (§8.1.3) to confirm no regression → re-run `fence:calibrate-semantic --anchors` (the 7d harness) since the Estatuto's chunk boundaries feed into what `/compare-scope` can find, and the fence's calibrated thresholds (`0.78`/`0.66`) were measured against the *pre-re-chunk* corpus state — a re-chunk of any actively-compared document is exactly the kind of corpus-state change `deploy.md` §4b already flags as invalidating the n=2 anchor calibration ("re-run `fence:calibrate-semantic --json`… do not treat 0.78/0.66 as final until n grows"). This is not new work Sprint 8 invents — it's the existing standing instruction, triggered by this sprint's own evidence-gathering.

## 9. Access & privacy

Per ADR-0018 (three load-bearing rules, quoted in full in §1) and spec §6's access matrix:

| Screen | super_admin | hr_agent | knowledge_editor | auditor |
|---|---|---|---|---|
| Analítica (§1-3) | ✅ | ✅ | ❌ | ✅ (read-only) |
| Cobertura (§4) | ✅ | ✅ | **✅ (coverage only — per spec §7 acceptance criterion)** | ✅ (read-only) |
| Quality review (§5) | ✅ | ✅ | ❌ | ❌ (spec: sampling review is `hr_agent`/`super_admin` only, not `auditor`) |
| Any conversation drill-down from any of the above | gated by `history.view_all` **or** `escalation.work`, exactly as today | only via card-scoped access if the sample/turn has a card; else needs `history.view_all` (which `hr_agent` lacks) | never | via `history.view_all` |

**The one new ability decision**: `knowledge_editor` seeing **coverage only** (not analytics, not sampling) is new — today's `EnsureCan`/`RoleSeeder` grants `knowledge.edit` to `knowledge_editor` (`RoleSeeder.php:33`) but nothing coverage-shaped exists yet to gate. **Decision: add a new ability, `analytics.view`, granted to `super_admin`/`hr_agent`/`auditor`; and gate the Cobertura screen specifically on `analytics.view` OR `knowledge.edit`** (so `knowledge_editor` reaches coverage via their existing ability, without gaining `analytics.view` itself and therefore without gaining Analítica or quality review) — this is the minimal new-ability surface that satisfies the spec's matrix exactly, reusing `knowledge.edit` rather than inventing a `coverage.view` ability nobody else needs. Quality-sample review reuses `escalation.work` (§6.5) — no new ability there. **Every one of these is server-gated via the existing `EnsureCan` middleware** (`EnsureCan.php:22-32`, unchanged) and **double-gated on the frontend** exactly as `AdminShell.tsx:71-75/96-98` already does for Directory/Admins/History (nav hidden **and** body re-checks the ability) — the same recipe, two new `canViewAnalytics`/`canViewCoverage` helpers in `lib/api.ts` next to the existing ones (§10).

**Drill-downs never bypass the logged path (the hard constraint, restated as a concrete rule):** every place this sprint lets an admin open a real conversation — from a cluster's example question, from a coverage gap's underlying document (which opens `DocumentDetailPanel`, not a conversation, so no log needed there), from a quality sample, from an escalation-by-fix row's linked card — either (a) reuses `EscalationCardDrawer`'s existing card-scoped view (already logged/gated the Sprint-4 way, unchanged), or (b) is the quality-sample review screen, which **must** call `ConversationAccessLogger::logView` itself (§6.3) since it is a genuinely new access path ADR-0018's two existing call sites don't cover. **There is no third kind of conversation view in this plan** — analytics and coverage are aggregates only (no `chat_session_id` ever reaches those screens' own queries), which is what makes "aggregates are free; any view of a conversation is logged" true by construction rather than by review discipline.
