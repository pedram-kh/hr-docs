# ADR-0025 — Staging deploy topology

**Status:** accepted

## Context
The four services (hr-backend, hr-ai, hr-frontend, Caddy) need a real, repeatable staging environment in `eu-west-1` — production-representative enough to test end-to-end (login, chat, ingest, backup/restore) without ECS/EKS/queue-broker complexity that isn't otherwise in scope (`hr-docs/sprints/staging-env/staging-env-spec.md`'s own out-of-scope list).

## Decision
- **Managed RDS (PostgreSQL 16 + pgvector) + S3**, one **EC2 `t3.large`** running all four services via **Docker Compose** — not ECS/EKS/SQS. Resized to `c7i.2xlarge` only transiently for ingest (`resize-for-ingest.sh`/`resize-back.sh`); the EBS volume (and everything on it, including the model-cache volume) is untouched by an instance-type change.
- **Secrets in SSM Parameter Store**, read at container-start via a shared `entrypoint.sh` using the **EC2 instance profile's credential chain** — never baked into an image, never written to disk inside a container, never a literal in `docker-compose.staging.yml`. Each mapping is explicit (`VAR=/ssm/path`), including cases where the same underlying secret maps to different env var names in different services (e.g. the shared internal token: `INTERNAL_TOKEN` for hr-ai, `HR_AI_INTERNAL_TOKEN` for hr-backend).
- **BGE-M3 (~4.3 GB) pre-cached in a named Docker volume** (`model-cache:/model-cache`, `HF_HOME` set explicitly in hr-ai's Dockerfile) rather than baked into the image — fetched once on first `docker compose up`, never re-downloaded as long as the volume persists. Gated by an **additive** `GET /health/model` endpoint (does not modify `/health` or `/health/config`) that Compose's healthcheck polls instead of the plain liveness probe, so `docker compose ps` correctly reflects the first-run download window.
- **The worker is the SAME hr-backend image**, unmodified, with `restart: unless-stopped` — only the container `command` differs (`php artisan queue:work --tries=3 --timeout=120` vs. the web service's `supervisord` running php-fpm+nginx).
- **IAM least-privilege via a Pedram-attached, narrowly-scoped inline policy** (`hr-staging-iam-bootstrap`, scoped to `hr-staging-*` role/instance-profile names only, no `AttachRolePolicy` of any managed policy) — attached in the console immediately before the one build step that needs it (`06-iam.sh`), detached immediately after. `cursor-dev`'s standing `PowerUserAccess` grant is never widened permanently.
- **S3 credentials, config only (ADR-0009 unaffected):** on staging, `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` are left **unset** for both hr-backend and hr-ai, so both fall back to the instance profile via each SDK's default credential chain — no long-lived static-key IAM user, which is exactly the thing an instance profile exists to avoid.
  - hr-backend needed **zero code change**: Laravel's `filesystems.php` S3 driver already omits the `credentials` array from the underlying `Aws\S3\S3Client` config when `key`/`secret` are empty (`Illuminate\Filesystem\FilesystemManager::formatS3Config()`), letting the AWS SDK's own default provider chain (which includes the EC2 instance metadata service) take over automatically.
  - hr-ai's `boto3.client()` has no equivalent auto-omission — passing `aws_access_key_id=""`/`aws_secret_access_key=""` explicitly makes `boto3` treat them as (invalid) credentials rather than falling back. This required one small, additive code change in `hr-ai/app/storage.py`: omit the `aws_access_key_id`/`aws_secret_access_key` kwargs entirely when both are empty/unset, so `boto3` falls back to its own default credential chain. Local dev (MinIO, `AWS_ACCESS_KEY_ID`/`SECRET` always set) is unchanged. `endpoint_url`/region handling is untouched.
- **No domain/TLS yet** — plain HTTP on the Elastic IP for first bring-up (`docker-compose.staging.yml`'s Caddyfile is a single `:80` block). Swapping in a domain later is a one-line Caddyfile change (Caddy's automatic HTTPS), not a topology change.
- **Postmark not available yet** — staging runs `MAIL_MAILER=log` (the rendered email, including the OTP code, lands in `storage/logs/laravel.log`). `hr-docs/infra/compose/otp.sh` reads it from there so login can be verified end-to-end without a real inbox. Switching to Postmark later is a `MAIL_MAILER`/`POSTMARK_API_KEY` env change, not a code change (and fixes the `POSTMARK_TOKEN`/`POSTMARK_API_KEY` naming mismatch found in `hr-backend/.env.example`/`config/services.php` — staging always uses the correct name).
- **Build on the EC2 itself, no ECR** — `deploy.sh` clones all four repos at pinned commit SHAs into `/opt/hr-staging/` and runs `docker compose build` there. Simpler for a first cut; revisit if `t3.large` build time proves too slow.
- **The Anthropic answer-model key is never SSM/env** (ADR-0015 unaffected) — it stays exactly where it is today: entered once via the hr-backend admin "Answer model" screen, `Crypt`-encrypted in `answer_model_settings`, passed to hr-ai per call.

## Consequences
- Every HR staging resource is named `hr-staging-*` and tagged (`Project=hr-platform`, `Env=staging`, `ManagedBy=hr-docs/infra`) — safe to share the AWS account with other unrelated projects.
- A "rollback" is just `deploy.sh` re-run with an older set of four SHAs — no separate rollback machinery.
- Cost stays in the `$4-5/day` range running 24/7 (`hr-docs/sprints/staging-env/plan.md` §8); `stop.sh`/`start.sh` bring that to ~$0.45/day when idle.
- Production re-run: this ADR's decisions (RDS+S3+single-EC2-Compose, SSM+instance-profile secrets, named-volume model cache) are intended to carry over; only the constants in `hr-docs/infra/vars.sh` change. The IAM attach/detach console dance is flagged (plan §9 item 4) as worth reconsidering for a dedicated, permanently-scoped deploy IAM user before go-live — explicitly deferred, not decided here.
