# ADR-0026 — OCR engine: Claude vision (`claude-opus-5`), chosen from measured eval numbers

**Status:** accepted

## Context
Sprint 7e adds an OCR fallback for scanned/text-less pages (`sprint-07e/plan.md`). The hard constraint set at kickoff: the engine is chosen **after** an eval against human-corrected gold, not assumed in advance — "column integrity beats CER," and the decision is recorded here with the actual measured table (mirroring ADR-0024's calibration-recorded-in-ADR precedent rather than a threshold fixed a priori).

Two candidates were built and scored for the eval only (`sprint-07e/eval/engines/`): **Claude vision** (`claude-sonnet-4-5`, page image in → structured `columns[]`/`table_rows[]` JSON out, es/eu tagged) and **Tesseract** (`spa+eus` traineddata, PSM 3, word-level bboxes fed through `hr-ai`'s real, unmodified `_classify_page`/`_es_ratio`). Textract was scoped as a conditional third candidate (Q2), wired only if the first two didn't cleanly bracket the decision.

5 fixtures: two two-column bilingual (es/eu) pages, one single-column Spanish page, one table/salary-grid annex, one low-quality/marginalia page. Gold: Claude-vision-drafted, then human-corrected line-by-line (full pass on the two two-column fixtures, lighter pass on the other three) — the drafting engine is scored against the corrected result like every other candidate, not exempted.

## Decision
**Claude vision (`claude-sonnet-4-5`) is the OCR engine**, decided by the measured eval table (full numbers, per-fixture breakdown, and the eu/es finding: `sprint-07e/review.md` §1):

- **Column integrity:** tied at 100% on both two-column bilingual fixtures — neither engine scrambles the es/eu reading order, the specific case the disqualifying rule names.
- **Table structure — the actual disqualifier:** Tesseract collapses the salary-grid annex into one garbled single-column blob (0 of 9 gold rows recovered, no `table_rows` structure at all). Claude vision preserves the full 9×7 grid at 87.5% cell-level accuracy. This is an unrecoverable structural loss for Tesseract on a real category in the backfill scope (doc 50's own tables), not a hypothetical — column-integrity-equivalent for tabular pages, and it disqualifies Tesseract outright per the same logic the two-column rule uses ("no code fixes a scrambled column/table after the fact").
- **Header survival** also favors Claude (76.7% vs 59.7% mean across all 5 fixtures), driven by Tesseract character-level misreads on citation-critical text (`Art. 12º-` → `Art. IZE`) that break `chunker.py`'s exact-match header detector even where the surrounding CER looks fine.
- **CER/WER** (secondary, per constraint): Claude ahead on both, but not the deciding factor — (1) above already resolves it.
- **Cost** (final tie-break, "if close"): not invoked — the quality gap isn't close. Claude costs ~$0.028/page vs Tesseract's $0, but the real backfill scope is ≤105 pages (`sprint-07e-build-prompt.md`), so projected total cost is ≈$3 — not a go-live concern.

**Textract was not wired.** The two candidates bracket cleanly: Tesseract's failure is table-structural (not the two-column-integrity failure the Q2 trigger names) and Claude's cost is trivial at backfill scale. No third engine was needed to resolve the decision.

**Sync vs. queued, decided by this eval's own number (§3.6):** Claude vision averages **38 sec/page** (9.7–69.7s range) at the model tested at that point (`claude-sonnet-4-5`). The OCR fallback runs **queued/async**, never inline inside `/extract`'s request/response cycle — a multi-page document would otherwise block for minutes. (This holds regardless of which Claude model is chosen below — even the fastest of the three candidates, `claude-sonnet-5` at ~23 sec/page, is still too slow for an inline HTTP request/response cycle.)

## Round 2 — which Claude model (run before Step 2 began)

The choice above fixed the **engine family** (Claude vision over Tesseract) but the model used throughout, `claude-sonnet-4-5`, was never itself a deliberate choice — it was simply `answer_model`'s default (`config.py:91`), reused for convenience when the eval harness was first built. Before starting Step 2, two newer models were run through the identical harness — same 5 fixtures, same prompt, same corrected gold, only the model string changed — and scored against `claude-sonnet-4-5`: **`claude-sonnet-5`** ($2/$10 per MTok in/out) and **`claude-opus-5`** ($5/$25 per MTok in/out). Full per-fixture table, the per-model p26 table-cell diff, and the revisited eu/es split: `sprint-07e/review.md` §1.5.

**Means across the 5 fixtures:**

| metric | sonnet-4-5 | sonnet-5 | opus-5 |
|---|---|---|---|
| Column integrity | 100.0% | 100.0% | 100.0% |
| Header survival (4 prose fixtures, fair comparison) | 95.75% | 100.0% | 100.0% |
| CER / WER (non-table) | 0.0143 / 0.0589 | 0.0029 / 0.0112 | 0.0018 / 0.0040 |
| Table cell accuracy (p26) | 87.5% | 98.4% | 100% adjusted (see review.md — raw row-count mismatch is a schema-placement artifact, not lost content: opus-5's 9 core salary-grid rows are byte-for-byte correct) |
| eu WER (2 bilingual fixtures, mean) | 0.2264 | 0.0157 | 0.0071 |
| Mean sec/page | 38.05 | 23.34 | 27.77 |
| Total cost, 5 pages / projected ≤105-page backfill | $0.1417 / ≈$2.97 | $0.1289 / ≈$2.71 | $0.3215 / ≈$6.75 |

**Decision rule applied in order (column integrity → header survival → table cells → eu WER → CER → cost):** column integrity ties all three. Header survival (fairly compared, excluding the p26 schema artifact both models are affected by) ties `sonnet-5`/`opus-5` at 100% and eliminates `sonnet-4-5` at 95.75%. Table cells favor `opus-5` (100% adjusted vs 98.4%) — close, resting on a manual re-alignment rather than a raw `score_ocr.py` number, but not contradicted by anything else. eu WER — the axis this round exists to re-check, since round 1 flagged eu accuracy as `sonnet-4-5`'s specific weak spot — favors `opus-5` by ~2.2x (0.0071 vs 0.0157). CER agrees. Cost, last: `opus-5` costs ~2.5x `sonnet-5` per page, but the absolute gap at backfill scale is ≈$4 total — not a go-live concern, so it does not override a decision already settled by quality.

**Decision: `claude-opus-5` is the OCR model.** `claude-sonnet-4-5` — the accidental default — is decisively beaten by both newer models and is dropped. Configured as `OCR_MODEL` (`hr-ai/app/config.py`'s `ocr_model`, default `"claude-opus-5"`), **deliberately decoupled from `answer_model`**: a future chat-quality-driven change to the answer model must never silently change the OCR engine, since the two were picked by two completely different evals for two completely different jobs. Same EU-endpoint constraint applies (`ocr_endpoint`, defaults to `answer_endpoint`, deploy.md §1).

## A finding carried forward, revisited — and it does not survive the model upgrade
Round 1 found that, split by column language on the two bilingual fixtures, `claude-sonnet-4-5` was near-perfect on Spanish (WER ≈ 0.2–0.8%) but materially worse on Basque (WER ≈ 22–24%) — a >25x relative gap, with Tesseract (which lost the overall decision) actually more accurate than `sonnet-4-5` specifically on the Basque column. **Re-run on the two newer models, this gap essentially disappears:** both `claude-sonnet-5` and `claude-opus-5` are under 3% WER on *both* languages, and on one fixture the eu column is measured as slightly *more* accurate than es. Read together, this looks like a `sonnet-4-5`-generation training-data-scarcity signature specifically — not a durable property of "Claude reading Basque" — and it is resolved by the model this ADR actually selects. The reviewer-guidance action from round 1 (scrutinize the `eu` column specifically when verifying an OCR'd bilingual page) is kept as a general habit, but it is no longer evidence of a structural weak spot in the chosen engine+model pair.

## Consequences
- OCR integration (Sprint 7e §3) is built against Claude vision, model `claude-opus-5` via the new `OCR_MODEL`/`ocr_model` config value: its already-column-split, already-language-tagged output is appended into `extract_language_streams`'s `es`/`eu` accumulators before the final sort (**Option B**), not injected as synthetic PyMuPDF-shaped geometry blocks (Option A, which would have been required for a bbox-only engine like Tesseract/Textract). The documented delta: Claude vision's units skip the furniture-stripping pass that native-PDF text and a bbox engine would both get.
- The OCR fallback is a **queued/async** job, not synchronous inside `/extract` — a direct consequence of the measured per-page latency (23–70 sec/page across all three models tried), not a guess.
- **`OCR_MODEL` is its own config value, never aliased to `answer_model`** (`hr-ai/app/config.py`) — this is now the second sibling to `router_model` in that file (small/fast classification model, independently chosen); OCR is the third independently-chosen model role.
- Per-page cost at the actual backfill scale (~$3–7 total for ≤105 pages, depending on model) is cheap enough that cost was never the deciding factor at either round; this may not hold if OCR scope grows well beyond the current backfill (e.g. routine ingest-time OCR of a large ongoing scan volume) — revisit the model choice against volume, not just per-page cost, if that changes. `claude-sonnet-5` is the number to re-check first if it does (small, already-small quality cost for ~2.5x less spend per page).
- The p26 gold-schema gap (table title lives outside both `columns[]` and `table_rows[]`, so no candidate was ever asked to place it consistently, and one model's placement choice happened to change its header-survival score) is noted as an eval-harness follow-up, not scored as an engine difference.
- If OCR volume or scope grows enough to revisit engine family (not just model), Textract remains the natural next candidate to trial (zero new dependency, `boto3` already present) — this ADR does not close that door, it just didn't need to open it now.

## Step 2 — integration consequences (built on this decision)

Full contract: `sprint-07e/review.md` §2. Summarized here because these are direct, load-bearing consequences of the engine/model choice above, not independent design picks:

- **Option B, not Option A.** Because Claude vision self-reports the column split and the es/eu language tag in its own JSON output (it already solved that problem visually — unlike a bbox-only engine such as Tesseract/Textract, which would have needed Option A's synthetic-geometry-block injection to let `extract_columns.py`'s existing `_es_ratio` gate make that call instead), the chosen integration shape appends the OCR result's pre-split, pre-tagged units directly into `extract_language_streams`'s `es`/`eu` accumulators, before the final sort — no synthetic PyMuPDF-shaped blocks, no re-derivation of language via `_es_ratio`.
- **The S3 sidecar (design choice (ii), not an `/embed` request-body field (i)).** `documents/{uuid}/ocr/{page:04d}.json`, written once by hr-ai at OCR time, holding the same envelope `/ocr-page` returns (`layout`, `columns`, `table_rows`, `article_headers`). `extract_language_streams(pdf_bytes, document_uuid=None)` probes for it only on a page with zero native blocks — the `/embed` request/response contract itself is untouched.
- **Queued/async, with an exact job/endpoint split (review.md §2.1).** `/extract` never calls the OCR model — it only marks a page `ocr_pending` within the page cap. hr-backend's `OcrDocumentPages` (ingest-time fan-out, one dispatch per document) enqueues one `OcrPage` job per pending page; each calls the shared `OcrService::ocrOnePage()`, which is reused verbatim, synchronously, by the Step-3 backfill command (no request deadline there, so no queue needed for that caller). `OcrPage::$timeout = 150` (worker default is 120s) specifically avoids a mid-call kill-and-retry that would double-pay for the same vision call.
- **The pinned table-placement contract (Round-2 Adjustment 2, review.md §1.6/§2.2).** The exact prompt scored in the eval is the exact prompt the production `ClaudeProvider.ocr_page()` uses: a table page's title lives *only* in `article_headers`; a footnote/plus-line block lives *only* in one `columns` `es` entry; `table_rows` holds *only* the grid. This was pinned specifically because §1.5's per-model table-title placement had been an unscored coin flip (a `score_ocr.py` harness bug, not a real quality difference, §1.6) — pinning it in the production prompt from the start means that ambiguity cannot recur on real backfill pages, independent of the harness fix.
- **The relaxed eu-verification rule (Round-2 Adjustment 1) — measured, not assumed.** Round 1 (`claude-sonnet-4-5`) measured a real, reproducible Basque weak spot (eu WER ≈ 22–24% vs es WER ≈ 0.2–0.8%, a >25x gap) that would have justified a separate "verify the Basque column" gate. Round 2's model choice (`claude-opus-5`, and `claude-sonnet-5` too) measured that gap **closing to under 3% WER on both languages** — the *specific number* that licenses dropping the separate gate: both language streams of an OCR'd bilingual page now ride the identical `under_review → confirm → embed` path, with the eu-scrutiny habit kept only as reviewer-facing guidance text (`ocr_bilingual` marker, no second approval step, no held-back stream). Had `sonnet-4-5`'s round-1 numbers been the ones shipped, this adjustment would not have been safe to make — the relaxation is a direct, measured consequence of the Round-2 model upgrade, not an independent policy choice.
- **Provenance is per-page, three-valued, and additive.** `document_pages.extraction_source` (`text_layer` default | `ocr_pending` transient | `ocr` terminal) plus `ocr_quality`/`ocr_engine`/`ocr_cost_usd`/`ocr_bilingual` — one hr-backend migration, no `documents`-level column (the badge/count is derived, matching the existing `empty_text` pattern). hr-ai still never migrates (ADR-0007) — its only new writes are the S3 sidecar (an existing privilege) and, unchanged, `document_chunks`.
