# ADR-0020 — AI-proposed tagging is inert until verified; managed vocabulary approval

**Status:** accepted (Sprint 7a)

## Context

Sprint 1 built a deterministic filename parser that scopes a document from its name (convenio / territory / sector / type / validity). The **messy tail** — scans, no-`numero` filenames, ambiguous titles — lands `under_review` with a `reason = unresolved` review task, the parser's `raw_unmatched_values` recorded for later (Sprint-1 review). Sprint 7a adds the **LLM tagging tier**: an AI reads such a document's text and *proposes* its facets, so the human reviewer starts from a draft instead of a blank form.

This is the first time a non-deterministic actor touches the knowledge substrate, and it sits on the answerability/safety axis beside **ADR-0002** (controlled vocabulary — humans curate the safe surface), **ADR-0007** (hr-backend owns all writes; hr-ai is a stateless tool that never migrates), **ADR-0011** (managed vocabulary growth: agent proposes, human approves, variant→alias default), and **ADR-0015** (the external model is never trusted with a decision). The danger the comité de empresa / AEPD will probe: **"can a wrong AI guess become a retrievable answer without a human?"** The load-bearing fact discovered in the reality-check is that the embedding gate is `tagging_status != under_review` — `auto_proposed` (the clean-parse state) **is** embedded (42 docs → 3,494 chunks in the dev corpus), only `under_review` is excluded. So the precise harm to prevent is an AI write that flips a doc out of `under_review`, or that mutates the authoritative scope, making a guess instantly answerable.

## Decision

The AI is an **upstream, inert proposer**. Six load-bearing rules, enforced server-side and proven by test (`Sprint7aTagProposalInvariantTest`):

1. **`under_review` is the inert state; the AI never leaves it (INVARIANT 1).** An unresolved document is already `under_review` at ingest. The tagging tier (`TagProposalService`) **never writes `tagging_status`** — not `auto_proposed`, not `verified`. The embedding gate (`tagging_status != under_review`, `ChunksEmbed`) therefore keeps an AI-proposed document genuinely unretrievable (0 chunks) until a human acts. Only the unchanged Sprint-3 verify action (`DocumentController::confirm`) flips `under_review → verified`. The gate itself is **not touched** — tightening it to `= verified` was rejected, because that would change which 42 `auto_proposed` docs are currently retrievable (a behaviour change to the frozen answer loop).

2. **The AI writes ONLY `ai_agent` provenance, never the authoritative FK columns (INVARIANT 2).** A proposal persists as append-only `ai_agent` `tag_events` + **unverified** `ai_agent` `document_topics` (`verified_by` null) + `tagging_confidence`. It **never** writes `convenio_id` / `document_type_id` / `validity_*` / `retrieval_status`. The scope FKs — which decide *which employees receive a document* — change only by the human verify/reassign action. No AI write can alter scope or eligibility. (We deliberately do **not** pre-fill the FK columns "to make verify one-click": that would muddy the cleanest safety property.)

3. **hr-ai proposes; hr-backend persists (ADR-0007 preserved).** `POST /propose-tags` (guarded by the internal token) reads the page text hr-backend already holds and the **closed candidate vocabulary** hr-backend passes (the full tiny territory/sector/document-type lists + a convenio shortlist by parser hint), and returns a facet envelope. It writes nothing, holds no DB access, and never migrates. The model binds to provided ids/codes only; the adapter drops any out-of-set reference (the closed-vocabulary guarantee, ADR-0002) and records unresolvable values as `raw_unmatched_values` with a soft variant hint — **the AI never invents vocabulary**.

4. **Auto-trigger is a queued job, never synchronous ingest.** `DocumentIngestor` dispatches `ProposeDocumentTags` (queued) for a `reason = unresolved` document *after* the ingest transaction commits. LLM tagging is slow and ingest is batch; a tagging failure must never block or roll back ingest (the embed-background posture). The doc is already safely `under_review`, so a failed proposal simply leaves it in the human queue. A manual "re-suggest" endpoint exists for re-running it.

5. **Vocabulary growth is propose→approve; approval is a guarded human action.** The AI (and a `knowledge.edit` human) may only **propose** a vocabulary value (`vocabulary_proposals`). **Variant→alias is the default**: the deterministic resolver (`VocabularyProposalService::suggestVariant`, normalized similarity — no model dependency) pre-selects "fold into an existing value's aliases" above its threshold; "create a new value" is the deliberate fallback. **Approving** is gated by the new `vocabulary.approve` permission — **`super_admin` only** (the most-guarded write, beside `admin.manage` / `guardrails.manage`). A super_admin may **propose-and-approve** in one action (they are the approver). Convenios are **never** created via this flow (registry-owned, ADR-0011) — only alias-folded. Approval writes the alias/new value with provenance and resolves the originating document's `raw_unmatched_value` (it does **not** auto-write the doc's FKs — rule 2 holds).

6. **Succession is scope-based, human-confirmed, never auto-retired.** The expiry queue (`reviews:scan-expiry` → `document_review_tasks type=expiry`, the "within 90 days of `validity_end` OR already past while active" window, which also absorbs the Sprint-3 `date_expired_active` staleness signal) surfaces near-expiry prose. A human confirms "this succeeds that" → `predecessor_document_id` (the Sprint-1 stub) is written, **same-convenio candidates only** (different-convenio docs coexist; a successor in another convenio is rejected 422). The predecessor is retired (`historical`) **only** on an explicit `retire_predecessor` + `confirm_scope_change` — nothing auto-retires. The **AI suggestion** of succession candidates (successor / coexisting-sibling / conflict by meaning) needs the semantic-comparison machinery of Sprint 7d and is **deferred to 7d**; 7a builds only the human-confirmed lineage write-side.

## Consequences

- The documented answer to "can a wrong AI guess become answerable without a human?" is **no, by construction**: the AI never leaves `under_review` and never writes a scope FK, so the embedding gate keeps every proposal inert until a human verifies. This is the AEPD / comité de empresa answer beside ADR-0018/0019.
- The fuchsia `--provenance-ai` token (ADR-0012/0013, vanilla CSS) marks **unverified-AI only** — the review queue, the AI-proposed facets on the card, the proposed-vocabulary list. On verify/approve the live UI reverts to normal styling; the AI origin persists only as the `ai_agent` dot in the provenance timeline (history, not a live alert).
- The answer loop is **not** touched (2b frozen): `/propose-tags` is a separate upstream call; `/retrieve` `/route` `/synthesise` `/ground` and `ChatService` are unchanged.
- This sprint is **document-level facet tagging only** — not multi-scope fact segmentation (Sprint 7b), which **reuses this "inert until verified" spine** (an AI proposal stays `under_review` and writes only `ai_agent` provenance until a human verifies).
- Additive migrations only (`vocabulary_proposals`, the `vocabulary.approve` permission seed). The `ai_agent` lane, `predecessor_document_id`, and the `expiry` task type already existed — 7a is their first writer. hr-ai gains an endpoint, not a migration.
